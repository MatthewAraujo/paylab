# T4 — Persistence, recovery and failure modes

## Objective
Prove and, where needed, complete the production-local stack's restart policies, data/credential preservation and explicit failure behavior.

## Acceptance Criteria Served
AC-5, AC-6, AC-11 in ../PRD.md.

## Affected Files / Areas
`compose.production.yaml` (restart policies); opt-in flags in `scripts/check-production-stack.py`.

## Test-First Plan
- AC-5 → stop/start and `up --build` keep all Demo Store Wallet ids and authentication; initializer logs preservation → HTTP + Compose (opt-in restart flag) → catches reseeding or lost credential.
- AC-6 → mismatched credential and database volumes make initialization fail; API and console stay down; no data changed → throwaway Compose project with crafted volumes → catches reset-on-mismatch.
- AC-11 → killing the API or console process makes Docker restart it to healthy; initializer has no restart policy → `docker compose exec` kill + `ps` (opt-in flag) → catches missing restart policy or init loop.
- AC-7 (edge) → a failing migration keeps API and console unavailable → throwaway project → catches dependants starting after failed init.

## Implementation Notes
Failure-mode checks use a separate throwaway Compose project name and volumes, removed only after confirming they are the throwaway ones. Never alter the real production-local or development volumes. Docker does not restart merely unhealthy containers; do not add a watchdog.

## Dependencies
T3.

## Completion Signal
Opt-in smoke checks pass; manual failure-mode evidence recorded in the run summary.
