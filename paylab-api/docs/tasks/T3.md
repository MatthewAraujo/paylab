# T3 — Schema baseline: accounts, payments and the ledger

## Objective

Create the initial PostgreSQL schema through Prisma and a first migration: Merchants, API keys, Accounts, Payments and the two ledger tables, with all non-trigger constraints, plus the External Clearing Account for BRL.

## Acceptance Criteria Served

US-1..4 (provisioning data model), US-9..15 (wallets), US-29..34 (idempotency uniqueness), US-45 (one Payment to at most one Ledger Transaction), US-53..59 (structural part: positive amounts, direction column, foreign keys).

## Affected Files / Areas

- `prisma/schema.prisma` and one new migration; the migration file may include hand-written SQL parts (checks, partial unique indexes) that Prisma cannot express.
- Seed or migration step that inserts the BRL External Clearing Account.

## Test-First Plan

Integration tests against the Testcontainers database (direct SQL through the Prisma client):
- A Wallet must have a Merchant; the External Clearing Account must have none (check constraint on kind).
- Only one External Clearing Account per currency (partial unique index).
- A Ledger Entry with a zero or negative amount is rejected.
- A Ledger Entry referencing a missing Ledger Transaction or Account is rejected.
- Two Payments with the same Merchant and Idempotency Key are rejected; the same key for two different Merchants is accepted.
- A Ledger Transaction can be referenced by at most one Payment.
- The BRL clearing Account exists after migrations from an empty database.

## Implementation Notes

- Tables: merchants; merchant API keys (hash only, never the raw key); accounts (id, kind `WALLET` | `EXTERNAL_CLEARING`, merchant reference, currency, created timestamp); payments (id, merchant, source account, destination account, amount in centavos as a 64-bit integer, currency, status, failure reason nullable, idempotency key, request fingerprint, optional ledger transaction reference, timestamps); ledger transactions (id, created timestamp); ledger entries (id, ledger transaction, account, direction `DEBIT` | `CREDIT`, amount in centavos as a 64-bit integer, created timestamp).
- Balance convention: a Wallet's Balance is credits minus debits; funding debits clearing and credits the Wallet.
- Foreign keys are restrictive (no cascading deletes) so nothing can silently remove ledger history.
- Prisma returns 64-bit integers as `BigInt`; decide the conversion boundary now (domain uses a value object, T5) and note it here for later tasks.
- Status and direction are database enums or checked text; keep them in sync with the domain constants.
- Triggers are NOT part of this task (T4). Do not add indexes for history queries yet; they are benchmark subjects (T14). Add only what the constraints above need.
