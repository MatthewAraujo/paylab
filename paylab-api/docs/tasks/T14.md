# T14 — Experiments: concurrency strategy comparison

## Objective

Compare the baseline lock (ADR 0002) against serializable isolation with retry, optimistic versioning and advisory locks under contention, and document the trade-offs.

## Acceptance Criteria Served

US-52, US-79.

## Affected Files / Areas

- Benchmark and experiment code isolated from production paths (alternative settlement adapters live only in the experiment folder); results notes and ADR updates.

## Test-First Plan

- Reuse the concurrency scenarios of T10 as the correctness bar: every alternative must keep the Balance non-negative and the ledger balanced, or the experiment records exactly how it fails.
- Define the load shapes first: one hot Wallet with many concurrent debits, many Wallets with few debits each, and mixed credit and debit traffic.
- Measure throughput, latency percentiles, retry or abort counts and lock wait time for each strategy on the benchmark dataset.
- Include the stronger row lock mode as a control to show the cost of blocking credits.

## Implementation Notes

- Keep alternatives out of the production module; the baseline remains the implementation.
- Serializable requires a retry loop on serialization failures; count retries.
- Optimistic versioning needs a version column on the Wallet; implement it only in the experiment schema or a scratch migration that is not shipped.
- Advisory locks use a stable numeric key derived from the Account id; document collision considerations.
- Record results and reasoning in an ADR update that either confirms ADR 0002 or supersedes it.

## Dependencies

T10, T12.

## Completion Signal

A comparison document with measurements exists, the baseline is confirmed or superseded by an ADR, and no experiment code ships in the production build.
