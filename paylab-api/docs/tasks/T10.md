# T10 — Concurrency suite

## Objective

Prove under real parallel connections that Settlement is safe: no overspend, no deadlock, credits unblocked, one Payment per idempotency key, and resumable after a crash.

## Acceptance Criteria Served

US-33, US-35, US-47..52.

## Affected Files / Areas

- The concurrency test folder and its runner config (from T2). No production code unless a test exposes a real defect.

## Test-First Plan

Each test uses independent connection pools against the Testcontainers database and the global invariant check afterwards:
- 50 parallel Settlements of R$ 10 from a Wallet holding R$ 100: exactly 10 `SUCCEEDED`, 40 `FAILED` with `INSUFFICIENT_FUNDS`, final Balance zero, never negative.
- Parallel Settlements from different Wallets complete without waiting on each other (assert no lock wait by timing bound or by observing lock state).
- Crossed transfers A→B and B→A in parallel, many rounds: none deadlocks and all resolve.
- A credit into a Wallet while an outgoing Settlement holds the row lock is not blocked (hold the lock with an open transaction, then insert an entry crediting the Wallet from another connection and assert it commits).
- 20 identical requests with the same Idempotency Key at once: exactly one Payment and one Ledger Transaction.
- Fault injected between transaction one and two, then retry: exactly one Settlement.

## Implementation Notes

- Assertions are on final database state and counts, never on ordering of interleavings.
- Repeat randomized rounds enough times to make a broken lock fail reproducibly, while keeping the suite bounded in time.
- Verify the weak lock claim empirically: with the stronger lock mode the "credit not blocked" test should fail; record that as a note for the ADR trail.
- Run in its own CI job so the fast gate stays fast.

## Dependencies

T9.

## Completion Signal

The suite passes repeatedly (at least 10 consecutive runs locally) with no flakiness and a clean invariant check.
