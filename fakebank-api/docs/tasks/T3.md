# T3 — Create and read a Provider Transaction (immediate success)

## Objective

The first tracer bullet through every layer: an authenticated Client creates a Provider Transaction that succeeds immediately, its events are persisted in the same database transaction, and the Client reads it back by id.

## Acceptance Criteria Served

- AC-1 (`201`, `FBK-` id, `SUCCEEDED`, `completedAt` set).
- AC-3 (`400 VALIDATION_ERROR` for schema violations, `422 UNSUPPORTED_CURRENCY`, nothing persisted).
- AC-7 (read by id; unknown or other Client's id → `404 TRANSACTION_NOT_FOUND`).
- AC-9 (`401 UNAUTHORIZED` without a valid key).
- AC-27 for immediate success (`transaction.processing` then `transaction.succeeded`).
- AC-28 (database rejects `UPDATE`/`DELETE` on events).
- AC-34 (keys configured as SHA-256 hashes, constant-time comparison).
- Contributes to AC-12 (OpenAPI for these endpoints).

## Affected Files / Areas

- Environment: `FAKEBANK_CLIENTS` (comma-separated `clientId:sha256-hex`), validated at boot.
- Auth guard resolving the Client from `Authorization: Bearer <key>`; a script that prints the hash of a key.
- SQL migration: `provider_transaction` (id, client id, External Reference, Idempotency Key, request fingerprint, Amount as positive bigint, currency, status, Failure Code, applied Outcome, created/updated/completed timestamps; unique (client id, Idempotency Key); index (client id, External Reference, created at)); `provider_transaction_event` (event id, transaction id, type, status, Failure Code, occurred at) with triggers rejecting `UPDATE` and `DELETE`.
- Transactions module: `POST /v1/transactions`, `GET /v1/transactions/:providerTransactionId`, Zod request schema, representation `providerTransactionId, externalReference, status, amountMinor, currency, failureCode, createdAt, updatedAt, completedAt`.
- Repository writing the transaction and its events in one database transaction, using the T2 state machine.

## Test-First Plan

- AC-1 → valid request with no scenario → `201`, id matches `FBK-` + UUID, `SUCCEEDED`, `failureCode` null, `completedAt` set, Amount echoed as integer → e2e → wrong status code or status, float amounts.
- AC-27 → after AC-1, the event table holds exactly `transaction.processing` then `transaction.succeeded` for that id → e2e reading the database → events missing, duplicated or written outside the transaction.
- AC-3 → missing field, `amountMinor` `0`, negative, decimal (`10.5`) or string, External Reference empty or longer than 128 → `400 VALIDATION_ERROR`, row and event counts unchanged → e2e → invalid money accepted, partial writes.
- AC-3 → `currency: "USD"` → `422 UNSUPPORTED_CURRENCY`, nothing persisted → e2e → non-BRL accepted.
- AC-9 → no `Authorization`, malformed header, unknown key → `401 UNAUTHORIZED` with the envelope, on both endpoints → e2e → unauthenticated creation or reads.
- AC-7 → `GET` by id returns the same representation as creation → e2e → read model drifting from write response.
- AC-7 → unknown id and an id created by another configured Client → `404 TRANSACTION_NOT_FOUND` → e2e → cross-Client data leak.
- AC-28 → direct SQL `UPDATE` and `DELETE` on `provider_transaction_event` fail → integration → event history rewritable.
- AC-34 → boot fails on a malformed `FAKEBANK_CLIENTS` entry; a key whose hash is configured authenticates as that Client → unit on env parsing + e2e → plaintext keys required or bad config accepted silently.

## Implementation Notes

- Idempotency is T4; here the `Idempotency-Key` is read and stored but replay/conflict behavior is not implemented. Tests in this task always send a fresh key.
- Use `crypto.timingSafeEqual` over the digests; never log keys.
- Request fingerprint = normalized External Reference, Amount, currency (stored now, used by T4).
- Prisma for schema and simple reads; raw SQL is fine where atomicity is clearer (follow `paylab-api` ADR 0004 spirit, not its code).

## Dependencies

T1 (skeleton, test layers), T2 (state machine).

## Completion Signal

All tests above pass under `pnpm test`, `pnpm test:integration` and `pnpm test:e2e`; `/docs` documents both endpoints, their status codes and the error shape.
