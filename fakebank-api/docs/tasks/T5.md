# T5 — Lookup by External Reference

## Objective

Let a Client recover Provider Transactions when it never received the FakeBank identifier, by listing every one of its transactions that carries an External Reference.

## Acceptance Criteria Served

- AC-8 (list, oldest first, includes transactions with different Idempotency Keys, empty list when none, Client-scoped).

## Affected Files / Areas

- Transactions module: `GET /v1/transactions?externalReference=` returning `{ data: [...] }` with the standard representation.
- Repository query on (client id, External Reference) ordered by creation time, using the index created in T3.
- OpenAPI for the endpoint; `400 VALIDATION_ERROR` when the parameter is missing or invalid.

## Test-First Plan

- AC-8 → one transaction for `PAY-1` → `200` with a one-item list in the standard representation → e2e → wrong shape or field drift from the by-id read.
- AC-8 → two transactions for `PAY-1` created with different Idempotency Keys → both returned, oldest first → e2e → silent deduplication hiding a double submission, unstable order.
- AC-8 → unknown External Reference → `200` with `data: []` → e2e → `404` where recovery code expects an empty list.
- AC-8 → another Client has a transaction with the same External Reference → not included → e2e → cross-Client leak.
- AC-8 → missing or empty `externalReference` parameter → `400 VALIDATION_ERROR` → e2e → listing every transaction of the Client.
- AC-9 → no key → `401` → e2e → unauthenticated listing.

## Implementation Notes

- No pagination in October (one External Reference has few transactions); note it as a known limit in the service `CONTEXT.md` if it matters.
- Vocabulary: External Reference is not unique (see `CONTEXT.md`).

## Dependencies

T3.

Tests above pass under `pnpm test:e2e`; `/docs` documents the endpoint.
