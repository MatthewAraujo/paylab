# T9 — Create Payment: validation, authorization and idempotency

## Objective

Implement `POST /v1/payments` and `GET /v1/payments/:id` with the required `Idempotency-Key`, the two-transaction flow (ADR 0001) and the error model.

## Acceptance Criteria Served

US-16..28, US-29..36, US-37..44.

## Affected Files / Areas

- Application layer: a create-Payment use case that claims the Idempotency Key, persists `CREATED`, then calls Settlement; a get-Payment use case.
- Infra: payments controller, schemas, presenter, error translation (422 mapping), module wiring.
- E2E tests.

## Test-First Plan

E2E through HTTP:
- Valid Wallet-to-Wallet Payment returns 201 with `SUCCEEDED` and the ledger reflects it.
- Insufficient funds returns 201 with `FAILED` and `INSUFFICIENT_FUNDS`, no ledger rows.
- Invalid requests return 422 with the standard error body and create no Payment: missing Idempotency Key, zero or negative Amount, same source and destination, unknown Account, currency mismatch, non-integer Amount.
- Source that is another Merchant's Wallet: not-found style rejection, no Payment.
- Source that is the External Clearing Account: rejected, no Payment; funding is possible only through the internal path used by seeds and tests.
- Paying another Merchant's Wallet as destination succeeds.
- Withdrawal to the External Clearing Account works and respects funds.
- Idempotency: same key and same body returns the same Payment (same id and state) with no second ledger transaction; same key with a different body returns 422; a different Merchant may reuse the key; a failed Payment returns the same failure on replay even after funds arrive.
- Crash between the two transactions (fault injected after transaction one): the Payment stays `CREATED`, a retry with the same key resumes Settlement exactly once.
- `GET /v1/payments/:id` returns own Payments and not-found for others'.

## Implementation Notes

- Idempotency claim relies on the database unique constraint on (Merchant, key); on conflict, load the existing Payment and compare the request fingerprint.
- Fingerprint the normalized body (source, destination, amount, currency).
- The existing Zod validation pipe may answer 400; the PRD requires 422 for invalid requests, so adapt the pipe or the exception mapping and cover it with a test.
- Provide an internal, non-HTTP way to create clearing-sourced funding Payments (a use-case entry point used by seed scripts and tests). It must not be reachable from a controller.
- A retry that finds a `PROCESSING` Payment must not double-settle; rely on the Payment row state and the lock to keep this safe, and document the reasoning.
