Lendo o Compose do PayLab

Um único docker compose up --build sobe quatro containers. Ao final desta lição você consegue explicar, linha por linha, o que cada um faz e como eles se encontram.

Os seis tópicos da semana 1 (imagem vs container, Dockerfile, layers, volumes, networks, variáveis de ambiente, Compose) já estão todos no seu código. Em vez de estudar cada um em abstrato, vamos ler o código e dar nome ao que já está lá.

1. Imagem vs container

Uma imagem é um pacote imutável (sistema de arquivos + metadados) gerado a partir de um Dockerfile. Um container é um processo isolado rodando a partir de uma imagem.[1] A prova está no seu Compose: demo-init e api usam a mesma imagem e fazem coisas diferentes.

compose.yaml
x-api: &api                 # bloco reutilizável (âncora YAML)
  image: paylab-api-dev       # nome dado à imagem construída
  build: ./paylab-api         # Dockerfile que a gera
  ...
services:
  demo-init:
    <<: *api                  # herda tudo de x-api
    command: ["sh", "-ec", "pnpm prisma:migrate:deploy && ... docker-demo.ts"]
  api:
    <<: *api                  # mesma imagem, CMD padrão: pnpm dev

Uma imagem, dois containers: demo-init sobrescreve o CMD com migrações + seed e termina; api roda o CMD ["pnpm", "dev"] do Dockerfile e fica vivo. O x- marca um campo de extensão que o Compose ignora, e &api / *api são âncora e alias do próprio YAML.[2]

2. Dockerfile e cache de layers

Cada instrução gera uma layer. Se uma layer muda, todas as que vêm depois são refeitas.[3] Por isso a ordem importa:

paylab-api/Dockerfile
FROM node:24-bookworm-slim
WORKDIR /app
RUN apt-get install openssl ... && npm install --global pnpm@11.9.0   # muda quase nunca
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY prisma ./prisma                # o postinstall roda "prisma generate"
RUN --mount=type=cache,...  pnpm install --frozen-lockfile   # caro: minutos
COPY . .                            # muda a cada edição de código
CMD ["pnpm", "dev"]

Copiando só os manifests antes do pnpm install, uma edição em src/ invalida apenas o COPY . .; a instalação continua em cache. O prisma entra cedo porque o script postinstall da API é prisma generate, que precisa do schema. O --mount=type=cache mantém o store do pnpm entre builds, mesmo quando a layer precisa ser refeita.[4] E o .dockerignore impede que node_modules e .env do host entrem no contexto de build.

3. Volumes: nomeados e bind mounts

Seu Compose usa os dois tipos, para propósitos opostos:

TipoNo PayLabPara quê
Volume nomeado
gerenciado pelo Docker		postgres-data:/var/lib/postgresql/data
demo-credentials:/run/paylab		Dados que precisam sobreviver ao container: o banco e a API key da Demo Store.
Bind mount
pasta do host		./paylab-api/src:/app/src
./paylab-ui/src:/app/src		Hot reload: você edita no host, o nest --watch / next dev vê na hora.

Volumes são "persistent data stores for containers, created and managed by Docker".[5] Um bind mount sobre uma pasta existente do container esconde o que a imagem tinha ali.[6] Repare que só src é montado, nunca a raiz: assim o node_modules instalado na imagem (Linux) continua visível. O sufixo :ro deixa a montagem só leitura: o ui pode ler a credencial, mas não alterá-la.

4. Rede e DNS

O Compose cria uma rede <projeto>_default (aqui, paylab-local_default, por causa do name: paylab-local) e "each service registers its name with an internal DNS server".[7] Por isso a DATABASE_URL aponta para o host postgres, não localhost.

A pegadinha mais importante do arquivo: a UI tem duas URLs para a mesma API.

PAYLAB_INTERNAL_API_URL: http://api:3333 — usada pelo servidor Next.js, que está dentro da rede.
NEXT_PUBLIC_PAYLAB_API_URL: http://localhost:3333 — usada pelo navegador, que roda no host e não conhece o nome api.

ports: "127.0.0.1:3333:3333" é IP_DO_HOST:PORTA_HOST:PORTA_CONTAINER; prefixar com 127.0.0.1 restringe o acesso à sua própria máquina. O postgres não tem ports: ninguém fora da rede consegue conectar nele.

5. Variáveis de ambiente e segredos

environment: injeta configuração no processo. Mas a API key não aparece em nenhum lugar do YAML: o demo-init a grava no volume demo-credentials, e o ui a lê na partida:

command: ["sh", "-ec", "export PAYLAB_API_KEY=$$(cat /run/paylab/api-key); exec pnpm dev ..."]

O $$ escapa o $ para o Compose não tentar interpolar; o $( ) chega intacto ao sh do container.[8] O exec faz o pnpm substituir o shell, recebendo os sinais de parada.

6. Ordem de partida

depends_on com condition transforma o Compose em uma pequena máquina de estados:[9]

  1. postgres fica healthy quando o healthcheck (pg_isready) passa.
  2. demo-init espera service_healthy, migra, faz o seed e sai com código 0.
  3. api espera service_completed_successfully do demo-init, depois fica healthy via fetch('/health').
  4. ui espera service_healthy da api.

Sem isso, a API tentaria conectar num banco ainda subindo, e a UI tentaria ler uma API key que ainda não existe.

Recupere da memória

Sem rolar a página para cima. Errar aqui é parte do treino.

1. Por que demo-init e api têm o mesmo image e fazem coisas diferentes?

  1. São dois containers da mesma imagem com comandos diferentes
  2. São duas imagens distintas que compartilham o mesmo nome
  3. São o mesmo container reiniciado com outro comando depois

Imagem é o molde; container é o processo. command sobrescreve o CMD do Dockerfile só para aquele container.

2. Por que o Dockerfile copia package.json e o lockfile antes do COPY . .?

  1. Para o Node achar o package.json antes de todo o código
  2. Para o pnpm install não rodar a cada mudança de código
  3. Para a imagem final ocupar menos espaço no disco do host

Mudou uma layer, tudo depois dela refaz. Com os manifests isolados, editar src/ só invalida o COPY . ..

3. Dentro do container api, a DATABASE_URL usa o host postgres. Por que isso funciona?

  1. O Postgres sempre publica a porta 5432 no host local
  2. O arquivo /etc/hosts da imagem Node já contém esse nome
  3. O Compose registra cada serviço no DNS da rede padrão

Todo serviço entra em paylab-local_default e é resolvível pelo nome. Aliás, o Postgres aqui nem publica porta.

4. Por que a UI usa http://api:3333 no servidor, mas http://localhost:3333 no navegador?

  1. O navegador roda no host, fora da rede do Compose
  2. O nome api só funciona com HTTPS e certificado válido
  3. O Next.js bloqueia nomes curtos em requisições do cliente

O DNS do Compose só existe dentro da rede. O navegador chega na API pela porta publicada no host.

5. O que acontece com os dados do banco depois de docker compose down (sem -v)?

  1. Somem, pois o container que os guardava foi removido
  2. Ficam na pasta paylab-api/data do host, via bind mount
  3. Ficam no volume nomeado, que vive fora do container

down remove containers e a rede, mas não volumes nomeados; só down -v os apaga.[10]

6. Qual é a ordem real de partida da stack?

  1. postgres saudável → api saudável → demo-init termina → ui
  2. postgres saudável → demo-init termina → api saudável → ui
  3. demo-init termina → postgres saudável → api saudável → ui

Cada condition espera o estado do anterior: service_healthy → service_completed_successfully → service_healthy.

Prove no terminal

Antes de cada comando, preveja a saída. Depois rode na raiz do repositório com a stack de pé (docker compose up --build -d).

  1. docker compose ps -a — qual container aparece como Exited (0), e por que isso é sucesso?
    respostademo-init: é um job de uma vez. Exit 0 é exatamente o que o service_completed_successfully espera.
  2. docker compose exec api getent hosts postgres — o que volta?
    respostaUm IP privado da rede bridge e o nome postgres: o DNS interno em ação. Rode docker network inspect paylab-local_default para ver os quatro containers ligados a ela.
  3. docker history paylab-api-dev — qual layer é a maior?
    respostaA do pnpm install (centenas de MB). É exatamente a layer que a ordem do Dockerfile protege do rebuild.
  4. Edite uma string qualquer em paylab-api/src e observe docker compose logs -f api.
    respostaO Nest recompila sem rebuild de imagem: bind mount + --watch. Desfaça a edição depois.
  5. docker compose down e depois docker compose up -d. Os dados continuam? Leia o log do demo-init.
    respostaSim: Existing demo data and credential preserved. Os volumes paylab-local_postgres-data e paylab-local_demo-credentials sobreviveram (docker volume ls).
