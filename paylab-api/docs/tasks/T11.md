# T11 — History, Payment list and daily report with keyset pagination

## Objective

Expose the read endpoints: Ledger Entry history per Account, Payment list with filters, and the daily volume report, all Merchant-scoped and keyset-paginated.

## Acceptance Criteria Served

US-62..70.

## Affected Files / Areas

- Application layer: list-entries, list-payments and daily-report queries.
- Infra: read controllers, cursor encode/decode helper, presenters, raw-SQL read adapters where the query shape matters.
- Integration tests for the queries and e2e for the endpoints.

## Test-First Plan

- Cursor helper unit tests: round trip, tampered cursor rejected as invalid.
- E2E history: newest first with a stable order for entries sharing the same timestamp (tie-break by id); following the cursor never repeats or skips across pages, including with rows inserted between page requests; last page returns no cursor; another Merchant's Account is not-found.
- E2E Payment list: same pagination; filters by Account, status and period work alone and combined; results only include the caller's Payments.
- E2E report: counts and volume per day and per status match known fixtures; only own data; empty range returns an empty result.
- Page size default and maximum are enforced.

## Implementation Notes

- Keyset ordering is creation time descending then id descending, comparing the pair as a row value.
- The public contract is cursor-only; offset exists only as a benchmark experiment in T14 and must not be exposed.
- Start with the minimum indexes the constraints already give. Index choices for these queries are the subject of T14; do not pre-optimize, but record the exact query text used so the benchmark can reuse it.
- Days in the report use one documented timezone (UTC) for September.

## Dependencies

T9.

## Completion Signal

Integration and e2e tests pass and the exact SQL of each read query is documented for T14.
