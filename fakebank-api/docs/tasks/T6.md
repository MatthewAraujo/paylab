# T6 — Lab surface and business Outcomes

## Objective

Introduce the lab surface behind its flag, Simulation Scenario registration, atomic consumption of scenario attempts, and the two business Outcomes: `FAIL` and `DEFERRED`.

## Acceptance Criteria Served

- AC-13 (registration, validation of combinations, replacement).
- AC-14 (`FAIL` → `201` `FAILED` with Failure Code).
- AC-15 (`DEFERRED` → `202` `PROCESSING`, stays pending).
- AC-20 for `FAIL`/`DEFERRED` (`times: N` affects exactly N attempts, then immediate success).
- AC-23 (scenarios scoped to the Client).
- AC-29 (lab endpoints `404` when disabled).
- AC-30 (boot refused with lab enabled in production).
- AC-12 (lab endpoints documented only when enabled).

## Affected Files / Areas

- Environment: `FAKEBANK_LAB_ENABLED` (default false) with the production refusal.
- SQL migration: `simulation_scenario` (client id, External Reference unique together, Outcome, delay, Failure Code, retry-after seconds, remaining attempts).
- Scenarios module: registration (`POST /__test/scenarios`, upsert), attempt decision (conditional decrement `remaining > 0` returning the Outcome, else immediate success).
- Lab module registered only when the flag is on (routes absent otherwise, so they 404 like unknown routes); Swagger includes lab routes only then.
- Transactions creation flow: for a new row, consume an attempt and apply `FAIL` or `DEFERRED` inside the same database transaction (via the T2 state machine).
- The registration schema accepts all six Outcomes now (`SUCCEED`, `FAIL`, `DEFERRED`, `RATE_LIMIT`, `ERROR_BEFORE_COMMIT`, `ERROR_AFTER_COMMIT`), `delayMs` 0–120000, `failureCode` (required for `FAIL`, rejected otherwise), `retryAfterSeconds` 1–3600 (only `RATE_LIMIT`), `times` 1–100 default 1. Behavior of the transport Outcomes and delays is T8.

## Test-First Plan

- AC-29 → flag off: `POST /__test/scenarios` and the advance route → `404` with the envelope → e2e → lab exposed by default.
- AC-30 → booting with `NODE_ENV=production` and the flag on throws at startup → e2e (pattern of `paylab-api` `benchmarks-production.e2e-spec.ts`) → scenario injection deployable.
- AC-13 → valid registration → `201` echoing the scenario → e2e → registration silently ignored.
- AC-13 → `FAIL` without `failureCode`, `failureCode` on `SUCCEED`, `retryAfterSeconds` on `FAIL`, `times: 0`, `delayMs: -1` or above the max, unknown Outcome → `400` → e2e → impossible scenarios stored.
- AC-13 → registering again for the same External Reference replaces Outcome and remaining attempts → e2e → stale scenario leaking between tests.
- AC-14 → `FAIL` with `INSUFFICIENT_FUNDS` → `201`, status `FAILED`, `failureCode` set, `completedAt` set; events `processing`, `failed` → e2e → business failure reported as a transport error or missing reason.
- AC-15 → `DEFERRED` → `202`, `PROCESSING`, `completedAt` null; a later `GET` still `PROCESSING`; only the `processing` event → e2e → pending treated as decided.
- AC-20 → `FAIL` with `times: 2` → attempts 1 and 2 fail (distinct Idempotency Keys), attempt 3 succeeds → e2e → off-by-one in consumption, scenario never expiring.
- AC-23 → Client A registers `FAIL` for `PAY-1`; Client B's attempt for `PAY-1` succeeds and A's scenario is untouched → e2e → cross-Client interference.
- AC-1 → no scenario registered → behavior identical to T3 → e2e (existing T3 tests stay green) → default path regressed.

## Implementation Notes

- The decrement must be a single conditional statement so parallel attempts cannot share one attempt (AC-22 is proven in T8's concurrency test).
- Keep the Outcome decision in the scenarios module and the status transition in the state machine; the transactions flow just composes them.
- Store the applied Outcome on the transaction for diagnosis only; never let it influence later behavior.
