# T8 — Transport Outcomes and delay

## Objective

Implement the Outcomes that fail at the transport level and the post-persistence delay, including their interaction with idempotent replays and parallel attempts. This is the core of the "ambiguous outcome" lab.

## Acceptance Criteria Served

- AC-16 (`RATE_LIMIT` → `429 PROVIDER_RATE_LIMIT`, `Retry-After`, nothing persisted).
- AC-17 (`ERROR_BEFORE_COMMIT` → `503 PROVIDER_UNAVAILABLE`, nothing persisted).
- AC-18 (`ERROR_AFTER_COMMIT` → persisted `SUCCEEDED`, `500 PROVIDER_INTERNAL_ERROR`; retry returns `200` with it).
- AC-19 (delay after persistence; client timeout leaves exactly one transaction).
- AC-20 for all Outcomes (`times: N`, e.g. `RATE_LIMIT` once then `201`).
- AC-21 (pre-persistence Outcomes apply even on a persisted key; replays consume nothing else and are not delayed).
- AC-22 (N parallel attempts with `times: K` → exactly K scenario-shaped responses).

## Affected Files / Areas

- Transactions creation flow, in this order: authenticate → validate → if the Client's scenario for the External Reference is pre-persistence (`RATE_LIMIT`, `ERROR_BEFORE_COMMIT`) and has attempts left, consume one, wait `delayMs`, answer the error → idempotency (T4): replay returns current state with no consumption and no delay → for a new row, consume an attempt, apply `SUCCEED`/`FAIL`/`DEFERRED`/`ERROR_AFTER_COMMIT` (persisting `SUCCEEDED` for the last) in one database transaction → commit → wait `delayMs` → respond (`201`/`202`/`500`).
- `Retry-After` header (default 1 or `retryAfterSeconds`).
- Error codes `PROVIDER_RATE_LIMIT`, `PROVIDER_UNAVAILABLE`, `PROVIDER_INTERNAL_ERROR`, all `retryable: true`.
- Concurrency suite: parallel attempts against a scenario.
- OpenAPI: document `429`, `500`, `503` on creation.

## Test-First Plan

- AC-16 → `RATE_LIMIT` → `429`, `Retry-After: 1`, envelope `retryable: true`; no row, no event → e2e → rate limit leaving partial state.
- AC-16 → `retryAfterSeconds: 30` → `Retry-After: 30` → e2e → configuration ignored.
- AC-20 → `RATE_LIMIT` `times: 1`, then retry with the same key and body → `201` → e2e → retry blocked forever or key burned by the failed attempt.
- AC-17 → `ERROR_BEFORE_COMMIT` → `503`, nothing persisted; retry with the same key → `201` and exactly one transaction → e2e → unsafe retry after a pre-commit failure.
- AC-18 → `ERROR_AFTER_COMMIT` → `500 PROVIDER_INTERNAL_ERROR`, yet a lookup by External Reference shows one `SUCCEEDED` transaction with both events → e2e → error response rolling back, or no record of the work.
- AC-18 → retry with the same key → `200` replay with that transaction, no second row → e2e → ambiguous failure producing a double charge.
- AC-19 → `SUCCEED` with `delayMs: 1500` and a client timeout of 300 ms → client times out; the transaction already exists during the delay; after the delay, retry with the same key → `200` with exactly one transaction → e2e → delay before persistence, lost work, duplicate on retry.
- AC-19 → `FAIL` with a delay → persisted `FAILED` before the response → e2e → delay applied to the wrong phase.
- AC-21 → persisted key, then a `RATE_LIMIT` scenario registered for its External Reference → the replay gets `429` and the attempt is consumed; the next replay gets `200` → e2e → pre-persistence Outcome bypassed by idempotency.
- AC-21 → persisted key, then a `FAIL` (or delayed `SUCCEED`) scenario registered → replay returns `200` immediately and the scenario's remaining attempts are unchanged → e2e → replay consuming or being delayed by post-persistence scenarios.
- AC-22 → `RATE_LIMIT` `times: 3`, 10 parallel attempts with distinct keys → exactly 3 `429` and 7 `201` → concurrency suite → attempts shared or lost under parallelism.

## Implementation Notes

- Every delay after persistence must happen after the database transaction commits, never while holding it open (long transactions would hide the ambiguity and hold locks).
- Delays use a timer that does not block other requests; tests keep delays short.
- `ERROR_AFTER_COMMIT` combined with `FAIL` semantics is out of scope (PRD Further Notes).

## Dependencies

T4 (idempotency flow), T6 (scenario registration and consumption).

## Completion Signal

Tests above pass under `pnpm test:e2e` and `pnpm test:concurrency`.
