# T18 — Demo database and seed

## Objective

Let a developer see the whole Operational Console with realistic data, without touching the development database: a separate `paylab_demo` database, filled by an insert-only, idempotent seed.

## Acceptance Criteria Served

New requirement from the Operational Console: every screen (Dashboard, Accounts, Payments, Ledger) needs multi-day, multi-Wallet data with both `SUCCEEDED` and `FAILED` Payments, more than one page of history, and a second Merchant to show isolation.

## Affected Files / Areas

- `scripts/demo/guard.ts` (database safety guard), `scripts/demo/plan.ts` (pure, deterministic data plan), `scripts/demo/apply.ts` (SQL writes and the invariant check), `scripts/demo.ts` (CLI).
- `package.json` scripts, `.env.example` (`DEMO_DATABASE_URL`), `PROJECT.md`.
- Tests: unit for the guard and the plan, integration for the writes.

## Test-First Plan

- Guard: accepts a local host and a database name containing `demo`; rejects a remote host, a name without `demo` (including `paylab`, `paylab_test`, `paylab_bench`) and a name that is not a plain identifier.
- Plan: deterministic for a seed; events are chronological; replaying the Settlement rule (funds sufficient means `SUCCEEDED`, otherwise `FAILED`) never produces a negative Balance; both statuses occur; the main Merchant has more than one page (over 20) of Payments and of entries for at least one Wallet; a second Merchant exists.
- Integration (real PostgreSQL): applying the plan leaves the global invariants intact and creates the planned rows; every API key authenticates its Merchant; a second run refuses with a clear error and writes nothing.

## Implementation Notes

- Insert-only: no `DELETE`, no `TRUNCATE`. The only destructive command is `demo:reset`, which drops the demo database itself, needs `--yes`, and passes the same guard.
- Every write goes through one transaction per run; the deferred ledger triggers validate each Ledger Transaction at commit, so the seed cannot bypass integrity. Timestamps are explicit (the write path always uses `now()`), following the test helpers.
- Payments carry the real request fingerprint, and funding is the same shape as the internal funding path (clearing debit, Wallet credit, a `SUCCEEDED` Payment from the clearing Account).
- API keys are generated once and printed once; only hashes are stored, so a second run cannot show them again and refuses instead.
- Runs only against a local host.

## Dependencies

T7, T8, T9, T16.

## Completion Signal

`pnpm demo:seed` creates and fills `paylab_demo` and prints two Merchant API keys; `pnpm demo:dev` serves the API on it; the console shows data on every screen; unit and integration tests pass and the invariant check reports no violation.
