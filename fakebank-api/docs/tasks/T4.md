# T4 — Idempotency

## Objective

Make `POST /v1/transactions` idempotent per Client and Idempotency Key: required header, replay returns the current state, conflicting reuse is rejected, and concurrent duplicates create one Provider Transaction.

## Acceptance Criteria Served

- AC-2 (missing `Idempotency-Key` → `400`, nothing persisted).
- AC-4 (replay → `200`, `Idempotent-Replayed: true`, same id, current status).
- AC-5 (same key, different body → `409 IDEMPOTENCY_KEY_REUSED`, original unchanged).
- AC-6 (keys scoped per Client).
- AC-31 (N parallel identical requests → one transaction, one pair of events, same id everywhere).

## Affected Files / Areas

- Transactions module creation flow and repository: insert guarded by the unique (client id, Idempotency Key) constraint; on conflict, load the existing row and compare request fingerprints.
- Header validation (1–255 characters).
- Concurrency test layer (`test:concurrency`), with a helper firing parallel HTTP requests against a listening server.
- OpenAPI: document `200` replay, `409`, and the `Idempotent-Replayed` header.

## Test-First Plan

- AC-2 → no header, empty header, 256-character key → `400`, no rows → e2e → creation without idempotency protection.
- AC-4 → same key and body twice → second is `200` with `Idempotent-Replayed: true`, same `providerTransactionId`, one row, two events total → e2e → duplicate transactions on retry.
- AC-4 → replay of a transaction whose status changed since creation returns the new status (arrange the change via direct SQL until T7 exists) → e2e → replay returning a stale stored response.
- AC-5 → same key with a different Amount, currency or External Reference → `409 IDEMPOTENCY_KEY_REUSED`, original row and events unchanged → e2e → key reuse silently creating or mutating.
- AC-6 → two Clients, same key → two distinct transactions, each Client's replay returns its own → e2e → cross-Client collision or leak.
- AC-31 → 20 parallel identical requests → exactly one row and two events; all responses carry the same id; exactly one is `201`, the rest `200` replays → concurrency suite → check-then-insert race creating duplicates.
- AC-31 → parallel requests with the same key but different bodies → one transaction, the others `409` → concurrency suite → conflicting body winning the race unnoticed.

## Implementation Notes

- The unique constraint is the only arbiter (same principle as `paylab-api`'s `PaymentSubmitter`); do not lock-then-check.
- Replay never re-applies a scenario or delay (those arrive in T6/T8; leave a clear single place in the flow where T8 hooks pre-persistence Outcomes before the idempotency lookup).
- The replay response is built from the current row, not from a stored body.
