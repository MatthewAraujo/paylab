Imagem vs container

Imagem: molde imutável em layers. Container: processo isolado criado a partir de uma imagem. command no Compose sobrescreve o CMD do Dockerfile.

Cache de layers

Mudou uma layer → todas as seguintes refazem. Ordem: base → ferramentas → manifests → install → COPY . .. RUN --mount=type=cache preserva o store do pnpm entre builds.

Volumes

Nomeado (postgres-data): gerenciado pelo Docker, sobrevive ao container e a down. Bind mount (./src:/app/src): pasta do host, para hot reload; esconde o que havia no destino. :ro = só leitura.

Rede

Rede padrão <projeto>_default; serviço = hostname. Dentro da rede: postgres:5432, api:3333. Do host/navegador: só portas publicadas, localhost:3333.

Ports

"IP_HOST:PORTA_HOST:PORTA_CONTAINER". 127.0.0.1: limita à sua máquina. Sem ports = inacessível de fora da rede.

YAML do Compose

x-nome: campo ignorado pelo Compose. &ancora define, *ancora reutiliza, <<: *ancora mescla. $$ = $ literal, sem interpolação.

Comandos de diagnóstico

docker compose up --build -d          # sobe em background, rebuildando imagens
docker compose ps -a                  # estado e health de cada container
docker compose logs -f api ui         # logs ao vivo
docker compose exec api sh            # shell dentro do container
docker compose exec api getent hosts postgres   # testa DNS interno
docker network inspect paylab-local_default     # quem está na rede
docker volume ls                      # volumes nomeados
docker history paylab-api-dev         # layers e tamanhos
docker compose down                   # remove containers e rede; mantém volumes
docker compose down -v                # ⚠ também apaga volumes (dados e credencial)

Quando rebuildar

Editou src/ → nada (bind mount + watch). Editou package.json, lockfile, Dockerfile ou .dockerignore → docker compose up --build.
