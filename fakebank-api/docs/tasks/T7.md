# T7 — Advance a deferred Provider Transaction

## Objective

Let a test decide a `PROCESSING` Provider Transaction explicitly, through the state machine, recording the terminal event.

## Acceptance Criteria Served

- AC-24 (`PROCESSING → SUCCEEDED`, or `FAILED` with a Failure Code; `completedAt` set; `FAILED` without a code → `400`).
- AC-25 (terminal → `409 INVALID_TRANSITION`, unchanged; other Client's or unknown id → `404`).
- AC-27 for deferred transactions (only `processing` until advanced, then the terminal event).

## Affected Files / Areas

- Lab module: `POST /__test/transactions/:providerTransactionId/advance` with body `{ status: SUCCEEDED | FAILED, failureCode? }`, Client-scoped, present only with the lab flag.
- Transactions repository: status-guarded update (`WHERE status = 'PROCESSING'`) plus the event insert in one database transaction.
- Error mapping of the state machine's invalid transition to `409 INVALID_TRANSITION`.
- OpenAPI for the route (lab only).

## Test-First Plan

- AC-24 → `DEFERRED` transaction advanced to `SUCCEEDED` → `200`, `completedAt` set; a later `GET` agrees; events `processing`, `succeeded` → e2e → pending never resolvable, missing terminal event.
- AC-24 → advanced to `FAILED` with `ACCOUNT_BLOCKED` → `200`, `FAILED`, code set → e2e → failure reason dropped.
- AC-24 → `FAILED` without `failureCode`, or an unknown status (`PROCESSING`) → `400` → e2e → invalid decisions stored.
- AC-25 → advancing a `SUCCEEDED` or `FAILED` transaction → `409 INVALID_TRANSITION`, row and events unchanged → e2e → terminal status rewritten.
- AC-25 → unknown id and another Client's id → `404 TRANSACTION_NOT_FOUND` → e2e → cross-Client control.
- AC-25 → two parallel advances on the same `PROCESSING` transaction → exactly one `200`, the other `409`; one terminal event → e2e with parallel requests → double decision race.
- AC-29 → flag off → `404` → e2e → advance reachable without the lab.

## Implementation Notes

- The status guard in SQL is what makes the parallel case safe; the state machine check alone is not enough under concurrency.
- An idempotent replay of the original request (T4) after advancing returns the new status, closing AC-4's "current status" case without direct SQL.
