# T16 — List the Merchant's Wallets

## Objective

Expose `GET /v1/accounts`, a keyset-paginated list of the authenticated Merchant's Wallets, so a read-only client (the Operational Console) can discover Account ids instead of needing them in advance.

## Acceptance Criteria Served

Extends US-9..15 (Wallets) and US-62..70 (keyset reads). New requirement from the Operational Console: browse Wallets without knowing their ids.

## Affected Files / Areas

- Application: `ListAccountsUseCase`, a `listWallets` query on `ReadQueriesRepository`.
- Infra: SQL text in `read-queries-sql.ts` (mirrored in `docs/reads-sql.md`), Prisma adapter, controller route, presenter, module wiring.
- Tests: integration for the query, e2e for the endpoint, doc-sync spec.

## Test-First Plan

- Integration: `listWallets` returns only the Merchant's Wallets, never the External Clearing Account or another Merchant's Wallets; newest first, id descending on ties; keyset position resumes without repeats or skips.
- E2E: `GET /v1/accounts` returns `{ items, nextCursor }` with `id`, `kind`, `currency`, `createdAt`; pagination via `limit` and `cursor`; default and maximum page size; unknown parameters (`offset`, `page`) rejected; another Merchant's Wallets absent; a Merchant with no Wallet gets an empty page; unauthenticated is 401.
- Doc sync: `docs/reads-sql.md` contains the exact SQL.

## Implementation Notes

- Same contract as the other lists: cursor-only, `limit` default 20 and max 100, ordered `created_at DESC, id DESC`.
- The Balance is not part of the list item: it costs a scan per Wallet (see CONTEXT.md performance facts). Clients read it per Wallet from `/balance`.
- `GET /v1/accounts` must not collide with `GET /v1/accounts/:id`.
- No new index in this task; a Merchant's Wallet count is small. Revisit if measured otherwise.
